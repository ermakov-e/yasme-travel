# Workflow агента

Единый процесс для любой задачи: от текста в трекере до готового PR. Процесс обязателен для фич и изменений логики; для опечаток и правок документации достаточно шагов 6–8.

## Схема

```text
Intake → Spec draft → Approval → Plan → Implementation → Gates → Docs sync → Review → Done
```

## Шаг 1. Intake

Вход: текст задачи, ссылка на трекер, скриншот, устное описание.

Действия:

1. Прочитать `AGENTS.md`.
2. Открыть [карту контекста](context-map.md) и определить область.
3. Найти существующую спеку по области (`docs/specs/**`).
4. Проверить, не покрыта ли задача уже готовой или черновой спекой.

Выход: решение — обновить существующую спеку или создать новую.

## Шаг 2. Spec draft

Создать спеку:

```bash
pnpm spec:new groups "Название задачи" --layer features
```

Заполнить:

- **Контекст** — зачем задача, что уже есть.
- **Требования** — проверяемые пункты.
- **Сценарии приёмки** — конкретные действия и ожидаемый результат.
- **FSD** — слой и модули, направление зависимостей.
- **Файлы** — существующие файлы/каталоги в `files`, новые — в `planned`.
- **Данные и контракты** — типы, эндпоинты, изменения API.
- **Проверка** — команды и ручные сценарии.
- **Открытые вопросы** — всё, что требует решения человека.

Правила:

- Требование должно быть проверяемым. «Сделать красиво» — не требование.
- Один сценарий приёмки = один наблюдаемый результат.
- Если не хватает информации — остановиться и задать вопрос, не додумывать.

## Шаг 3. Approval

- `draft` → `approved` переводит человек (или агент по явному указанию).
- До `approved` код не пишется.
- Мелкие правки в рамках уже согласованной спеки не требуют повторного approval, но фиксируются в разделе «Открытые вопросы» или в теле спеки.

## Шаг 4. Plan

Составить план реализации:

1. Список файлов (сверить с `files` / `planned`).
2. Порядок изменений: типы → модель → API → UI → маршруты.
3. Влияние на существующие сценарии.
4. Какие проверки подтвердят каждый сценарий приёмки.

Если план требует файлов вне спеки — сначала обновить спеку.

## Шаг 5. Implementation

- Соблюдать [fsd.md](../fsd.md) и [component-guidelines.md](../component-guidelines.md).
- Стили — только через тему.
- Новые компоненты — в правильный слой; переиспользуемые — в `shared/ui`.
- Первичный файл реализации пометить `// @spec <id>`.
- Если по ходу выяснилось, что требование неверно, — обновить спеку, затем код.

## Шаг 6. Gates

Обязательные команды:

```bash
npx tsc --noEmit
pnpm lint
pnpm docs
pnpm docs:check
```

Дополнительно:

- `pnpm docs:check -- --strict` — если задача касается архитектуры или слоёв.
- Ручной прогон сценариев приёмки в `pnpm dev`.

Гейт не пройден — задача не готова. Нельзя «закомментировать проверку», чтобы пройти.

## Шаг 7. Docs sync

1. Перевести статус спеки в `done`.
2. Обновить `updated` (дата).
3. Заполнить `tests`, если тесты появились.
4. Запустить `pnpm docs` и убедиться, что generated отражает новое состояние.
5. Проверить [generated/traceability.md](../generated/traceability.md): спека связана с файлами.

Если задача изменила архитектуру — добавить или обновить ADR в `docs/decisions/`.

## Шаг 8. Review

Ревьюер проверяет по [definition-of-done.md](definition-of-done.md):

- соответствие спеке;
- отсутствие нарушений слоёв;
- отсутствие хардкода стилей;
- наличие проверок и обновлённой документации;
- отсутствие регрессий.

Формат замечаний: `файл:строка`, проблема, ожидаемое поведение, severity.

## Шаг 9. Done

Задача считается готовой, когда:

- все сценарии приёмки выполнены;
- гейты зелёные;
- спека в статусе `done`;
- generated закоммичен вместе с кодом.

## Правила изменения спеки

| Ситуация | Действие |
|---|---|
| Уточнение формулировки без изменения поведения | править спеку, статус не менять |
| Новый сценарий или требование | добавить в спеку, вернуть статус в `approved` при существенном изменении |
| Требование отменено | пометить в спеке, при необходимости — `deprecated` |
| Задача разрослась | разделить на несколько спек со ссылками друг на друга |

## Когда задавать вопрос

- Неясен ожидаемый результат сценария.
- Требуется изменить публичный контракт API или доменную модель.
- Нужна новая зависимость.
- Задача затрагивает больше двух слоёв неочевидным образом.
- Спека противоречит существующему коду или другой спеке.

## Частые ошибки

| Ошибка | Как избежать |
|---|---|
| Код без спеки | шаг 2 обязателен |
| Спека «на будущее» без критериев | каждый пункт — проверяемый |
| Правка generated | только `pnpm docs` |
| Импорт `features` из `shared` | проверять `architecture-check.md` |
| Забыли обновить статус | шаг 7 в чек-листе |
| Тесты «потом» | зафиксировать в `tests` и DoD |
