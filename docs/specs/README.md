# Спеки задач

Спека — единица требования. Она отвечает на вопросы: **зачем**, **что должно работать**, **в каких файлах**, **как проверить**. Код без спеки в проекте не пишется.

## Расположение

```text
docs/specs/
├── README.md
├── _template.md
├── auth/
│   ├── 001-mock-auth.md
│   └── 002-session-persistence.md
├── groups/
├── map/
├── photos/
└── platform/
```

- `area` — доменная или техническая область (`auth`, `groups`, `map`, `photos`, `platform`).
- Файл: `NNN-slug.md`, где `NNN` — порядковый номер внутри области.
- ID спеки: `<area>-<NNN>`, например `groups-002`.

## Создание

```bash
pnpm spec:new groups "Создание группы"
# или с явным slug и слоем:
pnpm spec:new groups "Создание группы" --slug create-group --layer widgets
```

Скрипт создаёт файл по шаблону с корректным ID и датой.

## Frontmatter

```yaml
---
id: groups-002                 # уникальный ID
title: Создание группы         # человекочитаемое название
status: done                   # draft | approved | in-progress | done | deprecated
layer: widgets                 # основной слой FSD
areas: [groups]                # области
files:                         # существующие файлы и каталоги (валидируются)
  - src/widgets/create-group-modal/
planned: []                    # плановые пути (проверяются только по префиксу)
tests: []                      # пути к тестам
created: 2026-11-22
updated: 2026-11-22
---
```

Правила:

- `files` может содержать каталог с завершающим `/` — он покрывает все файлы внутри.
- `planned` — для путей, которых ещё нет; они не валидируются на существование.
- Даты в формате `YYYY-MM-DD`.
- `id` не меняется после создания.

## Статусы

| Статус | Значение | Кто переводит |
|---|---|---|
| `draft` | черновик, требования уточняются | автор спеки |
| `approved` | согласована, можно реализовывать | человек или агент по указанию |
| `in-progress` | идёт реализация | исполнитель |
| `done` | реализовано и проверено | исполнитель после гейтов |
| `deprecated` | устарела или отменена | автор или ревьюер |

## Обязательные секции

- `## Контекст`
- `## Требования`
- `## Сценарии приёмки`
- `## FSD`
- `## Файлы`
- `## Проверка`

Дополнительно рекомендуется: `## Данные и контракты`, `## Открытые вопросы`, `## Ссылки`.

## Маркер `@spec`

Первичный файл реализации помечается комментарием:

```ts
// @spec groups-002
```

Это связывает код со спекой в [generated/traceability.md](../generated/traceability.md). Маркер проверяется: он обязан указывать на существующую спеку.

## Проверка

`pnpm docs:check` валидирует:

- уникальность `id`;
- допустимые `status` и `layer`;
- наличие обязательных полей и секций;
- существование путей из `files`;
- корректность префиксов `planned`;
- маркеры `@spec`;
- актуальность generated-страниц;
- битые ссылки в документации.

## Правила качества

- Требование должно быть проверяемым.
- Сценарий приёмки — конкретное действие и ожидаемый результат.
- Не описывайте реализацию детальнее, чем нужно для проверки; архитектурные решения — в ADR.
- Если требование изменилось — сначала спека, потом код.
- Спека не дублирует другой документ: ссылайтесь, а не копируйте.
